数据层

store.py建 catalog.sqlite 和 labels.sqlite，事务写入、重复忽略、冲突拒绝。
prepare.py把 raw 文件分批写入数据库，做官方划分和 dev/full 范围控制。
audit_store.py统计查询、商品、标注、标签、外键、候选数量并输出报告。

准备顺序

  1. 核验 manifest。
  2. 筛选 US small_version=1。
  3. 官方 train 按查询文本组分为 train/validation，官方 test 保持 test。
  4. 写 queries、judgments 和 catalog。
  5. 执行外键、重复、标签和数量审计。
  6. 审计通过后原子发布 dataset。

catalog.sqlite只保存商品目录；labels.sqlite保存查询、公开标注和 partition。在线服务不加载 labels.sqlite。

检索层：BM25、向量与 RRF

BM25

把商品文本建成倒排索引，根据词频、文档频率和文本长度计算分数。零命中返回空结果，同分按商品键稳定排序。

向量召回

Sentence Transformers 将查询和商品编码为向量。第一版使用分块 NumPy 精确点积作为正确性真值，向量与商品键单独保存并做 hash 校验。精确版本通过后再接 FAISS。

RRF

score(product) = sum(1 / (60 + rank_in_each_retriever))

RRF 只使用排名，不把 BM25 和 cosine 分数直接相加。相同商品合并，并保留各路来源。

排序层：特征与 LightGBM

特征包括查询和标题 token 数、词项重合、brand/color 命中、BM25 分数、dense 相似度、RRF 分数和字段长度。特征函数不接收 Judgment，因此不能直接读取标签。

训练标签为 I=0、C=1、S=2、E=3；DCG gain 单独为 0、1、3、7。每个 query 是一个 LightGBM group。训练只使用 train，validation 用于 early stopping，test 在配置冻结后评估一次。

评估层：两个范围不能混

给定候选排序候选来自公开 qrels，比较模型在同一候选集中的排序质量，主指标 NDCG@10 和 MRR_E@10。
目录检索候选来自完整 US 商品目录，报告 known_E_recall@100、judged_fraction@100、空结果率和延迟。

未被公开标注的商品是 unknown，不自动当成 I。分母为空的查询记为 undefined 并报告数量。ANN Recall 只表示近似索引相对于精确向量的重合率，不是业务相关性召回。

服务层

SearchEngine 执行输入校验、BM25/dense 召回、RRF、特征、ranker 重排和 SearchResult 输出。ranker 缺失时可以降级到 RRF，但响应必须写明 pipeline。

FastAPI 提供 /health、/version、/search。使用 lifespan 启动时加载共享模型和索引；响应返回 release_id、pipeline、request_id 和阶段耗时。错误响应不泄漏路径、堆栈、标签和密钥。

最终验收

  • 数据版本、SHA256、SQLite 审计和查询划分可追溯。
  • BM25、dense、RRF、LTR 使用统一范围完成对照。
  • 报告包含 NDCG、MRR、known recall、延迟和至少三组消融。
  • validation 至少完成 30 个完整查询的错误分析。
  • 特征、索引、模型和 release 兼容性不匹配时会拒绝加载。
  • API 可以返回 health、version、search，重启后结果稳定。
  • README 可以让新人按命令启动 dev 流程。
  • 简历只写 reports 中真实存在的数字。

  • 为什么按 query 分组，而不是按 query-product 行随机切分？
  • 为什么 unknown 不能直接当 I？
  • 为什么 label 和 gain 分开？
  • 向量 ID 错位如何通过 metadata 发现？

  • 没有 GPU 时为什么主线仍然可以完成？
