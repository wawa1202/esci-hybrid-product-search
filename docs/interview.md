# 商品搜索项目面试问题库

本文只描述当前项目已经实现或已经验证的内容。面试时可以说“本项目实现/验证了……”，不要把尚未运行的完整 US 目录、GPU 性能和真实线上指标说成已经完成。

## 一、先背熟的项目介绍

### 1. 请用一分钟介绍这个项目

**答：**这是一个基于公开 Amazon ESCI 数据的商品搜索系统。用户输入商品需求后，系统先用 BM25 做关键词召回，再用本地 `all-MiniLM-L6-v2` 做向量召回，通过 RRF 融合两路候选，最后用 LightGBM LambdaRank 做学习排序。项目还包含数据审计、发布包校验、离线评估、FastAPI 服务和搜索页面。当前在 Windows RTX 4060 笔记本的 CPU 环境完成了 dev/validation 流程，服务器没有 GPU 也能运行。

### 2. 这个项目解决了什么业务问题？

**答：**输入一句自然语言商品需求，从商品库中返回更相关的商品，并尽量让 Exact 商品排在前面。工程上要拆开两个问题：商品有没有进入候选集，以及进入候选集后顺序是否合理。这样当结果不好时，可以判断是召回不足还是排序错误。

### 3. 为什么选择 ESCI？

**答：**ESCI 提供查询、商品和 query-product 关系标签，适合演示真实搜索系统的召回、排序和评估闭环。它是公开数据，便于复现，也避免声称使用 Amazon 内部数据。局限是公开数据的分布、规模和线上行为信号不能代表企业真实生产环境。

### 4. 系统完整链路是什么？

**答：**原始数据先经过读取、标准化、身份校验和分区，写成 catalog 与 labels。索引阶段构建 SQLite BM25 倒排索引和归一化 MiniLM 向量。在线查询时同时走 BM25 和 dense，RRF 合并候选，补齐两路分数后用 LambdaRank 重排，最后通过商品库补回标题和品牌。FastAPI 只负责请求校验、生命周期和并发控制，算法集中在 SearchEngine。

### 5. 为什么没有直接用大语言模型？

**答：**这个项目的核心任务是结构化商品检索和排序，不需要生成答案。LLM 可以用于查询改写、意图识别或解释，但会增加延迟、成本和不稳定性。先把召回、排序、指标和数据边界做正确，才有必要引入 LLM 做增量能力。

### 6. 这个项目哪些部分可以写进简历？

**答：**可以写公开数据搜索系统、混合召回、RRF、Learning to Rank、离线评估、发布包校验和 FastAPI 服务。指标要写成“在公开 ESCI dev/validation 上测得”，不能写成线上 CTR 或业务收入提升。当前真实结果是 NDCG@10：BM25 0.7682、dense 0.7829、RRF 0.7777、LTR 0.7735；LTR 没有超过 dense。

### 7. 当前实现最大的工程取舍是什么？

**答：**优先保证可解释、可复现和 CPU 可运行。向量检索使用分块精确搜索，作为 ANN 的正确性基准；索引和模型都写入新目录并用 manifest、SHA256 和 runtime signature 校验；validation 用于开发，test 需要显式冻结后才能消费。这样牺牲了一部分大规模性能，但减少了学习阶段最容易出现的错配和数据泄漏。

### 8. 如果让你继续做生产化，你先改什么？

**答：**先补真实线上日志和人工/点击反馈，建立离线指标与线上业务指标的关联；再把向量索引替换为经过 recall-latency 验证的 ANN，并加入增量索引、灰度发布、监控告警和回滚。当前项目只有公开离线数据，不能直接当生产系统。

## 二、架构与数据边界

### 9. 为什么召回和排序必须分开？

**答：**商品库可能很大，召回需要低延迟地从全库缩小候选；排序可以在较小候选集上使用更多特征和更复杂的模型。如果相关商品没有进入候选，后面的排序器无论多好都无法把它排出来。分层后也能分别优化召回 recall 和排序 NDCG/MRR。

### 10. `Query`、`Product`、`Judgment` 分别代表什么？

**答：**`Query` 是用户搜索请求，包含 query_id、文本和 locale；`Product` 是商品事实，包含商品 ID、标题、描述、品牌等；`Judgment` 是一个 query 与一个 product 之间的人工相关性关系，包含 ESCI 标签。标签不是查询本身的属性，因为同一查询对不同商品可以有不同标签。

### 11. 为什么商品身份不是只用 product_id？

**答：**项目把商品身份定义为 `(locale, product_id)`，查询身份定义为 `(locale, query_id)`。不同市场可能出现相同的裸 ID，只用 product_id 会产生跨市场碰撞，导致索引、标签和结果错误配对。

### 12. ESCI 四种标签分别是什么？

**答：**E 是 Exact，满足查询意图的精确商品；S 是 Substitute，可以替代满足需求的商品；C 是 Complement，是配套或互补商品；I 是 Irrelevant，与查询无关。S 和 C 不能简单合并为“差一点”，它们的业务含义不同。

### 13. 为什么未标注商品不能自动当作 I？

**答：**未标注只表示人工评审中没有这条关系，可能是没有抽到或没有标注，不等于不相关。把 unknown 强行设为 I 会制造假负样本，使排序模型和指标都产生偏差。项目把未知关系与 I 分开处理。

### 14. 训练标签为什么映射为 `[0, 1, 3, 7]`？

**答：**项目把 I、C、S、E 映射为 0、1、2、3，再用 LightGBM 的 `label_gain=[0,1,3,7]` 表示相关性等级之间的非线性价值。E 比 S 更重要，S 比 C 更重要。这个映射是建模假设，应该通过验证集和业务目标检查，不能说它是 ESCI 官方唯一映射。

### 15. 为什么训练、validation、test 要按 query 分组？

**答：**排序模型学习的是同一个 query 内候选商品的相对顺序，所以 group 必须表示一个查询及其候选。数据矩阵的连续行、标签和 group 长度必须严格一致。若把不同查询混在一个 group，模型会学习无意义的跨查询比较。

### 16. 如何防止 query 泄漏？

**答：**分区按 query group 进行，训练代码会检查 train 和 validation 的 query key 不重叠。测试集在模型选择阶段不读取；只有 validation 报告、release 和配置冻结后，才显式允许 test。

### 17. 为什么线上不加载 labels？

**答：**labels 是离线评估答案，线上加载会把人工答案带进服务边界，也容易发生标签泄漏。线上只需要 catalog、BM25、向量和可选 ranker；labels 只由离线评估流程读取。

### 18. 数据预处理为什么要标准化文本？

**答：**BM25 和特征计算必须使用一致的分词、大小写和字段拼接规则。项目把文本策略版本和最大 token 数写进产物身份，防止构建索引时用一套规则、查询或排序时用另一套规则。

### 19. 如何处理坏数据？

**答：**读取阶段做字段、类型、locale、ID 和标签校验；正常数据写入 SQLite，拒绝行写入 rejects 文件并记录原因。数据集 manifest 记录数量、分区和身份，audit 阶段再检查排序、重复、文件和统计信息。

## 三、召回系统

### 20. BM25 的作用是什么？

**答：**BM25 是关键词召回基线，能够利用商品文本中的词项、词频、逆文档频率和文档长度归一化。对品牌、型号、颜色和精确词很有价值。项目用 SQLite 保存倒排表，查询只读取命中 posting，不把整个倒排表加载到 Python 内存。

### 21. BM25 的核心公式是什么？

**答：**单个词项的贡献可以写成 `IDF * tf*(k1+1)/(tf+k1*(1-b+b*doc_len/avg_len))`，多个查询词的贡献求和。项目默认 `k1=1.2`、`b=0.75`，并对参数、文档长度、posting 和 IDF 做一致性校验。

### 22. 为什么还需要 dense 召回？

**答：**BM25 依赖词项重合，遇到同义表达、词形变化或查询与标题措辞不同的情况可能漏召回。dense 使用 MiniLM 把查询和商品编码到同一向量空间，再用余弦相似度寻找语义近邻，可以补充词面不一致的候选。

### 23. 为什么使用 `all-MiniLM-L6-v2`？

**答：**它体量较小、推理成本低、适合笔记本 CPU 教学和复现。项目固定模型 revision，并把 embedding signature 写入向量 manifest。它不是针对商品搜索专门训练的模型，所以 dense 结果不一定优于领域模型。

### 24. 向量为什么要 L2 归一化？

**答：**归一化后向量点积等价于余弦相似度，数值范围和比较口径稳定。项目保存前和加载时都会检查向量为 float32、有限、二维且范数接近 1；查询向量也必须满足同样约束。

### 25. 为什么使用分块精确向量搜索？

**答：**它逐块计算向量点积，用小堆保留 top-k，内存不会一次性构造整个相似度矩阵，同时结果可以作为 ANN 的正确性基准。缺点是全库扫描，数据规模变大后延迟会线性增长。

### 26. 为什么不直接把 BM25 分数和余弦分数相加？

**答：**两种分数的数值范围、分布和含义不同，直接相加需要额外归一化，而且归一化规则会影响结果。当前项目使用 RRF 按名次融合，避免跨模型分数量纲不一致。

### 27. RRF 怎么计算？

**答：**对商品在每个召回列表中的排名计算 `1/(constant + rank)`，再对不同来源求和。项目默认常数是 60，BM25 和 dense 各取 top 100，融合后保留 top 100。商品同时出现在两路时会得到更高的融合分数。

### 28. RRF 的优点和缺点是什么？

**答：**优点是无需校准分数，简单、稳定、可解释；缺点是只利用名次，忽略了分数差距，而且常数和各路 top-k 仍然需要验证。它不保证一定优于任何单一路径，当前报告中 RRF 的 NDCG 是 0.7777，高于 BM25 但低于 dense 0.7829。

### 29. 召回结果为什么要保留来源和原始排名？

**答：**这样可以解释商品是由哪一路找到的、在每一路排第几，也能区分“单路召回”和“两路共同召回”。这些信息用于调试和页面展示，不作为人工标签输入。

### 30. 如果某商品没有被 BM25 召回，为什么排序时不能直接把 BM25 分数当成缺失？

**答：**排序器需要在同一候选集上获得两路分数。项目对融合后的所有候选调用 `score_pairs` 补算分数；未命中关键词的 BM25 分数是 0，但这和商品不存在是不同情况。dense 也会补算候选的向量分数。

### 31. 召回 top-k 为什么不是越大越好？

**答：**增大 top-k 可能提高召回覆盖，但会增加向量计算、商品读取、排序特征和整体延迟，还可能给排序器带来更多噪声。应该在 recall、NDCG、延迟和内存之间做实验选择，而不是只追求最大候选数。

### 32. 如何判断问题出在召回还是排序？

**答：**先查看相关商品是否出现在全库召回候选中：没有则是召回问题；已经在候选中但最终位置不好，才是排序问题。项目分别报告 known E recall 和候选内 NDCG/MRR，就是为了支持这个定位。

## 四、学习排序

### 33. 为什么使用 LambdaRank？

**答：**搜索结果关注列表顺序，LambdaRank 直接围绕排序位置和 NDCG 优化，比普通回归更贴合目标。它适合在每个 query 的候选集合内学习商品相对顺序。

### 34. 当前 LTR 使用哪些特征？

**答：**固定 11 个特征：`bm25_score`、`dense_score`、`query_length`、`title_length`、`overlap_count`、`overlap_ratio`、`brand_match`、`color_match`、`bullet_length`、`bullet_overlap_count`、`bullet_overlap_ratio`。特征顺序写入模型清单，预测时必须完全一致。

### 35. 为什么特征里可以有 BM25 和 dense 分数？

**答：**它们是检索信号，不是标签。排序器可以学习在不同查询条件下如何组合两路证据；但分数必须通过同一版本的索引和编码器生成，不能使用不兼容的产物。

### 36. 为什么不把 product_id、query_id 和标签放进特征？

**答：**ID 没有稳定的语义，可能导致记忆训练样本；标签是答案，放入特征会泄漏。项目特征只基于查询、商品文本和检索分数，并测试了 query 独立性和 candidate-independent 行为。

### 37. 什么是 candidate-dependent feature，为什么要避免？

**答：**如果特征通过当前候选集合的最大值、均值或排名归一化得到，那么候选集合变化会改变同一个商品的特征，线上和离线口径容易不一致。当前特征使用绝对分数、文本长度和词项重合，避免依赖候选集合的归一化。

### 38. 为什么 LambdaRank 的 group 很重要？

**答：**模型需要知道哪些行属于同一个查询，才能计算查询内的 pairwise/listwise 排序信号。group 数组与 X、y 的连续行必须一一对应；项目会检查 group 非空、总和等于行数以及 train/validation 查询不重叠。

### 39. validation 在训练中做什么？

**答：**用于 LightGBM 的早停和开发阶段比较，不参与最终 test 结论。当前实现固定 CPU、线程数、随机种子和 deterministic 配置，减少重复运行时的非必要波动。

### 40. LTR 没有提升，项目是否失败？

**答：**不失败。它说明当前特征、标签、候选、模型和数据规模下，没有证据证明 LTR 优于已有方法。真实工程中能够诚实发现“复杂模型没有带来收益”，并定位下一步实验，比虚构提升更重要。下一步可以做特征消融、增加高质量行为特征、调整候选范围或换领域模型。

### 41. 如何做特征消融？

**答：**每次只删除一个或一组特征，例如 `dense_score`，写入新的模型发布目录，再用同一 validation 报告口径评估。不能修改已有模型文件，也不能把删除排序特征说成关闭了整条 dense 召回链路。

## 五、评估与实验设计

### 42. 为什么不能只看最终准确率？

**答：**搜索是排序问题，“准确率”无法说明相关商品排在第几，也无法区分没召回和排错。项目同时看候选内 NDCG/MRR、全库 known E recall、judged fraction、逐查询结果和错误案例。

### 43. NDCG@10 衡量什么？

**答：**它衡量前 10 个位置的折扣累计增益，越靠前的高相关标签贡献越大。它回答的是“在已评估候选内，相关性等级是否排得合理”，不是全库召回率，也不是线上点击率。

### 44. MRR_E@10 衡量什么？

**答：**它只关注第一个 E 商品出现的位置，越早越高。它适合回答用户能否很快看到一个精确匹配，但不能反映后面所有相关商品的完整排序。

### 45. known E recall@100 衡量什么？

**答：**它以已知 E 标签商品为分母，计算前 100 个全库候选找回了多少，主要衡量召回覆盖。它不把未标注商品当负样本，也不能代表所有真实相关商品的召回。

### 46. `judged_fraction` 有什么用？

**答：**它表示返回候选中有多少商品存在人工标签。比例低时，NDCG 等基于人工判断的结论覆盖有限；未标注商品不能因此被判为不相关。

### 47. 为什么要同时评估人工候选和全商品库？

**答：**人工候选适合分析排序器是否把已知相关商品排好；全商品库适合分析召回链路是否能找到相关商品。只做前者会漏掉召回问题，只做后者又看不清候选内部顺序。

### 48. 当前报告能否代表线上效果？

**答：**不能。当前报告是公开 ESCI dev 的 200 个 validation 查询和 11,934 件商品并集，适合学习、回归和开发诊断；没有线上点击、转化、库存、价格和真实流量分布，因此不能写成线上收益。

### 49. 为什么 validation 不能当 test？

**答：**validation 已经用于早停、比较和调参，继续根据它选择模型会产生选择偏差。模型和参数确定后，要冻结 release 与 validation 报告，再显式消费一次 test，才能得到更接近独立验收的结果。

### 50. 如何判断一个指标提升是否可信？

**答：**先确认数据集、查询集合、分区、top-k 和标签口径一致，再看逐查询差值和 bootstrap 置信区间。当前 LTR 相对 BM25 的 95% 区间跨 0，所以不能宣称显著提升。

### 51. 为什么要看逐查询指标，而不是只看均值？

**答：**均值可能被少量查询主导，逐查询结果可以发现哪些意图退化、哪些查询受益，以及模型是否只对某类商品有效。项目会输出 ranking-per-query、retrieval-results 和 error-analysis 文件。

### 52. benchmark 测量了什么？

**答：**它预热 5 次后采样搜索调用，输出 embedding、BM25、dense、fusion、ranking 和 total 的 p50/p95/p99。当前 benchmark 是本地 SearchEngine 的串行耗时，不包含 HTTP 排队、网络延迟，也不是并发 QPS 压测。

### 53. 为什么需要冻结机制？

**答：**冻结把选定的 release、validation 报告、哈希和评估口径固定下来，防止选完结果后反复挑 test。项目用一次性消费凭据限制同一版本的 test 流程；它是实验纪律，不是不可绕过的安全控制。

## 六、发布、服务与性能

### 54. `release.json` 解决什么问题？

**答：**它记录 release_id、dataset_id、runtime signature 和文件哈希，加载时检查发布包是否完整、文件是否被修改、配置是否兼容。这样可以避免 catalog、BM25、向量和 ranker 来自不同实验。

### 55. 为什么要校验 runtime signature？

**答：**模型和索引不仅依赖文件本身，还依赖文本版本、模型 revision、top-k、RRF 常数等运行参数。参数不一致可能导致“能加载但语义不一致”，所以加载阶段应直接拒绝。

### 56. 为什么新实验不能覆盖旧目录？

**答：**覆盖会破坏可复现性，也可能留下部分成功的混合产物。项目采用新目录、暂存构建、最后写 release 标记的方式；失败目录保留用于排障，成功历史不删除。

### 57. SearchEngine 启动时做什么？

**答：**先校验 release，再以只读方式打开 catalog、BM25 和向量索引，加载本地编码器，检查向量 signature；如果存在 `ranker.txt`，再加载 Ranker。任何资源不匹配都会在启动时失败，而不是等第一条请求才暴露。

### 58. 为什么 catalog 使用只读连接？

**答：**在线服务只需要查询商品事实，不应该在搜索请求中修改数据。只读连接降低误写风险，也让资源职责更清晰。

### 59. FastAPI 层为什么不直接写检索算法？

**答：**API 负责输入校验、错误边界、请求 ID、生命周期和并发限制；SearchEngine 负责算法流水线。这样算法可以被离线评估和 benchmark 直接调用，不必通过 HTTP，也避免页面/API复制业务逻辑。

### 60. 为什么 SQLite 只用一个工作线程？

**答：**SearchEngine 内的 SQLite 连接在工作线程创建、使用和关闭，避免跨线程使用连接。当前设置为一个 executor worker，保证资源生命周期简单；信号量把执行中和排队中的请求总数限制在配置值内，第三个请求会得到 503。

### 61. 为什么服务不把查询原文写日志？

**答：**查询可能包含用户隐私或敏感意图。当前日志只记录 request_id、release_id、pipeline、结果数量和阶段耗时，不记录查询原文和商品详情；问题排查依靠 request_id 和离线复现。

### 62. 如何降低在线延迟？

**答：**先用阶段耗时确定瓶颈，再分别优化。可能的方向包括缓存高频查询向量、扩大批量编码、调小候选数、把精确向量搜索替换为经过验证的 ANN、优化 SQLite 查询和控制排序特征数量。每次改动都要同时看 recall、NDCG、p95 和内存。

### 63. FAISS 为什么只是可选实验？

**答：**ANN 通常用更低延迟换取近似邻居，可能降低召回。项目先用分块精确搜索作为 correctness baseline，再用相同向量和查询比较 ANN 邻居 recall、延迟和内存；安装或使用 FAISS 本身不等于完成性能优化。

## 七、常见排障问题

### 64. 搜索结果为空，你怎么查？

**答：**先确认输入通过 query 校验，再检查服务加载的 release 和 locale；随后确认 BM25、向量、catalog 的键集合和 manifest 一致。再用同一 query 分别查看两路召回，区分商品库没有覆盖、文本策略问题、索引损坏还是排序阶段异常。

### 65. BM25 结果很差，你怎么查？

**答：**先检查查询和商品文本经过的版本、大小写、分词和字段拼接；再检查商品库是否有相关词、BM25 top-k 和 `k1/b` 参数。通过 `score_pairs` 和 posting 统计确认是词项没有命中，还是命中后排序不合理。

### 66. dense 结果很差，你怎么查？

**答：**检查模型 revision、向量维数、L2 归一化、查询和商品是否使用同一编码器，并确认向量 manifest 的 hash 没有变化。之后比较精确向量搜索的邻居和商品文本，判断是模型语义能力不足还是索引错配。

### 67. RRF 结果比单路更差怎么办？

**答：**先确认两路结果的 query、source、rank 连续且商品唯一，再看各路 top-k、RRF 常数和逐查询差异。融合不保证提升，可能是其中一路噪声较大或候选截断不合适；可以做常数和候选数的验证实验，但不能直接删除表现较差的一路而不看覆盖。

### 68. LTR 启动时报 signature mismatch 怎么办？

**答：**不要手改 manifest。比较 release 的 runtime signature、模型 manifest、当前配置和编码器 revision；如果不一致，使用匹配配置或从同一数据和配置重新构建索引、训练和评估。

### 69. 训练报 group 长度不一致怎么办？

**答：**检查每个 query 的候选行是否连续、标签是否和候选一一对应、group 总和是否等于 X/y 行数，以及是否在拼接 train/validation 时混入空组。不能通过删除最后几行来“修复”，必须回到数据构建阶段找身份或分区问题。

### 70. 为什么页面搜索和离线评估结果不同？

**答：**先确认 release、配置、模型、top-k、查询文本和 locale 一致。网页只展示在线候选和当前 top_k；离线报告还会使用人工标签、全库候选和固定评估 cutoff，两者回答的问题不同。

### 71. 端口被占用怎么办？

**答：**先确认是否是自己之前启动的搜索服务，优先在原终端正常停止；面板只停止自己创建的进程，不会强杀外部进程。不要随意结束未知进程，因为可能影响其他服务。

### 72. 测试有弃用警告，算失败吗？

**答：**看退出码和测试统计。当前全量结果是 139 passed、1 条上游 Starlette/httpx 弃用提示；警告需要记录和后续处理，但不等于当前测试失败。

## 八、面试官可能继续追问的设计题

### 73. 如果商品库扩大 100 倍，当前方案哪里先出问题？

**答：**精确向量搜索会先受到全库扫描和内存映射读取的影响，p95 延迟上升；BM25 的 SQLite posting、商品读取和 LambdaRank 候选排序也需要重新测量。会先建立规模化 benchmark，再引入 FAISS、Milvus 或其他 ANN，并用精确搜索验证近邻召回损失。

### 74. 为什么不直接使用 Milvus？

**答：**Milvus 适合大规模向量存储、索引和分布式服务，但当前项目需要先把检索算法、数据契约、评估和发布边界讲清楚。小规模学习阶段的本地精确索引更透明；规模上升后可以让 Milvus 负责 dense candidate retrieval，保留 BM25、RRF、LTR 和评估层。

### 75. 如果要加入 Milvus，接口怎么设计？

**答：**定义统一的 vector retriever 接口，输入归一化 query vector、locale 和 top-k，输出带 `(locale, product_id)`、rank、score、source 的 Hit。先用当前 VectorIndex 作为 exact 实现，再增加 Milvus 实现；离线比较两者的 ANN recall、NDCG、p95 和资源成本，确认后才切换默认实现。

### 76. 如果要加入 Kafka、Spark、Hive，它们放在哪里？

**答：**Kafka 适合接收搜索日志、点击和商品变更事件；Spark 适合大规模清洗、特征聚合和离线训练数据生成；Hive 或数据湖表适合保存原始事件、标签和宽表。当前项目是本地离线教学系统，不需要为了技术栈完整而强行引入它们。

### 77. 如果点击数据存在位置偏差，怎么处理？

**答：**不能把点击直接当作无偏相关性标签。需要考虑展示位置、曝光、设备和用户群体，使用随机探索、propensity weighting、去偏学习或人工标签校准，并按时间切分验证，避免未来信息泄漏。

### 78. 如何做线上 A/B 测试？

**答：**先固定两个可加载的 release，通过用户或请求稳定分桶，记录曝光、点击、加购、转化、无结果率和延迟。先检查护栏指标，再看主指标；同时保留离线报告和 release_id，保证线上结果可回溯。

### 79. 如果线上指标提升但 NDCG 下降，你怎么解释？

**答：**可能说明人工标签没有覆盖真实业务价值，或者模型提升了长尾商品、价格、库存和转化相关因素。需要检查标签覆盖、流量分布、指标定义和实验分桶，不能简单宣布某一个指标“错了”。

### 80. 如果面试官问“这个项目是不是只会调包”，怎么回答？

**答：**我实现了数据契约、分区和审计，设计了 BM25 SQLite 倒排、分块精确向量检索、RRF 融合、LambdaRank 特征与 group 构造、release 校验、离线评估和 FastAPI 资源生命周期。第三方库用于底层能力，但候选口径、标签边界、评估拆分、发布一致性和排障流程是自己设计并验证的。

## 九、面试时必须主动说清楚的边界

- 数据来自公开 ESCI，不使用 Amazon 内部数据、接口或线上指标。
- 当前完成的是 dev/validation 的可复现闭环；真实 test 没有在模型选择阶段提前消费。
- 当前 LTR 没有超过 dense，不能宣称“加入排序模型后效果显著提升”。
- 当前服务默认 CPU；GPU 只会缩短大规模编码或训练时间，不是系统正确运行的必要条件。
- FAISS HNSW 是独立可选实验，没有替换默认精确向量检索。
- Dify、聊天模型 API、Milvus、Kafka、Spark 和 Hive 不属于当前最小闭环的必要依赖；它们是后续生产化或扩展方案。

## 十、建议的回答顺序

面试官随便问一个算法点，都尽量按这个顺序回答：

1. 先说它在链路中的位置；
2. 再说输入、输出和为什么这样设计；
3. 再说当前项目的具体实现和参数；
4. 最后说验证方式、真实结果和局限。

例如被问“为什么用 RRF”，可以回答：它位于 BM25 和 dense 之后、LTR 之前，输入两路带排名的 Hit，输出统一候选；因为两路原始分数量纲不同，所以按排名用 `1/(60+rank)` 融合；当前报告显示 RRF 的召回覆盖优于 BM25，但排序 NDCG 没有超过 dense；后续还需要在更大规模和独立 test 上验证。
