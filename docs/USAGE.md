# 商品搜索项目：从体验到实验

这份指南按学习场景编排。第一次使用不需要打开终端，也不需要先下载数据、训练模型或配置 Dify。

## 先记住项目在解决什么问题

你输入一句商品需求，系统要完成四件事：

1. 从商品库中找出可能相关的候选商品；
2. 用关键词和语义两条路线互相补充；
3. 把两路候选融合，再用学习排序调整先后；
4. 用公开 ESCI 的人工标签检查“找到了多少”和“排得是否合理”。

这是一套商品搜索工程，不是聊天问答应用。它默认使用 US 市场和英文查询，运行在笔记本 CPU 上；Dify、聊天模型 API 和没有 GPU 的云服务器都不是本项目的必要依赖。

## 第一次打开：先体验现成结果

在项目根目录双击 `打开项目.cmd`。如果 Windows 弹出安全提示，确认文件位置是本项目目录即可。面板打开后，不要先做实验，先进入左侧第 1 页 **体验搜索**。

面板有四页，建议始终按这个顺序学习：

| 页面 | 你要完成的事情 | 形成的认识 |
|---|---|---|
| 体验搜索 | 像顾客一样输入需求 | 系统的输入、结果和召回来源 |
| 结果解读 | 读已有 validation 报告 | 指标分别回答什么问题 |
| 重做实验 | 建索引、训练、验证 | 每一步的输入、产物和依赖 |
| 学习路线 | 对照关卡回到源码 | 为什么这些文件按这个顺序存在 |

面板底部的日志用于排障。平时只看状态文字；只有失败时才点击“打开日志目录”或查看日志区域。面板关闭时，只会停止它自己启动的任务和搜索服务，不会替你结束其他终端启动的进程。

## 场景一：用三个需求观察搜索系统

### 1. 启动搜索页面

在“体验搜索”页选择已有的“学习排序”版本，点击 **打开搜索体验**。面板会先检查版本，再加载本地模型；第一次加载可能需要一些时间。看到“搜索已就绪”后，浏览器会打开本地搜索页。

如果同版本服务已经在运行，面板会直接连接它，不会重复启动。若端口上是另一个版本，面板会拒绝连接，并提示你先在原来的终端停止服务。

### 2. 搜索 `running shoes`

观察前 5 个商品，然后问自己三个问题：

- 结果是不是跑鞋，而不是鞋带、袜子或配件？
- 有没有一个看起来相关、但排得很靠后？
- 每个结果旁边的 `bm25 #…` 和 `dense #…` 是否同时出现？

这里的两种编号表示候选来源：BM25 是关键词召回，dense 是语义召回。只出现一路编号，说明该商品只被这一路带进了当前候选集；这不是“另一路给了零分”。

### 3. 搜索 `red running shoes`

这次增加颜色要求。观察前几名是否变化，并检查标题中是否真的出现红色线索。结果不变化也有价值：它可能说明当前商品文本、召回数量或排序特征没有充分利用颜色。

不要凭一个查询断言系统好或坏。这个页面用于提出问题，不能替代离线评估。

### 4. 搜索 `wireless headphones`

观察结果是否仍然围绕查询意图。你可以在页面记录一个“看起来合适”的商品和一个“值得怀疑”的商品，再回到项目中解释它们来自哪路召回。

完成这一关的标准是：你能说清楚“没有被召回”和“被召回但排错了”是两种不同问题。

### 5. 对比“仅融合”版本

回到面板，先停止本面板启动的服务，再在版本下拉框选择“仅融合”版本，重新打开搜索体验。这个版本使用 BM25、dense 和 RRF，但没有加载 LambdaRank 排序器。

切换后重复一个查询，观察 `pipeline` 或页面上的策略名称变化。这个操作让你看到 RRF 是一条可用的回退路径，而不是训练失败后的隐藏行为。

## 场景二：读懂已有成绩单

进入 **结果解读**。选择已有的 validation 报告。表格中的每一列只回答一个问题：

| 指标 | 它回答的问题 | 不应该怎样解释 |
|---|---|---|
| NDCG@10 | 人工候选内，相关商品是否排在更合理的位置 | 不是点击率，也不是线上收入 |
| MRR@10 | 第一个精确相关结果是否尽早出现 | 不是所有相关商品的完整覆盖 |
| known E recall@100 | 整个商品库中，已知 E 商品找回了多少 | 只对已知标注商品负责 |
| judged fraction | 返回候选中有多少有人工标签 | 未标注不等于不相关 |

当前报告的真实结果是：

- 人工候选 NDCG@10：BM25 `0.7682`、dense `0.7829`、RRF `0.7777`、LTR `0.7735`；
- 全商品库 known E recall@100：BM25 `0.8047`、dense `0.8636`、RRF `0.8750`；
- LTR 相对 BM25 的 95% 差值区间跨过 0，当前没有显著提升证据。

这组结果最适合用来学习工程判断：增加一个排序器并不自动带来提升；如果相关商品已经在候选集里，排序器才有机会改变顺序。如果商品根本没有被召回，应该先查召回链路。

报告页还会列出真实错误案例。把案例当作排障线索，而不是把一个案例夸大成总体结论。页面已经区分了“人工候选排序”和“全库召回”，不要把二者混成一个准确率。

## 场景三：亲手重做一轮开发实验

完成前两关后，进入 **重做实验**。这一页只操作 `dev` 数据集和 `validation` 分区，不会自动消费 test，也不会覆盖已有产物。

### 第 1 步：建立索引

选择已有的 dev 数据集，点击 **开始新一轮**，再点击 **1 建立索引**。

这一阶段把商品文本变成两种可检索结构：关键词倒排索引和 MiniLM 向量。等待状态显示任务完成后，理解这三个产物：

- 商品库：搜索命中后根据 ID 取回标题、品牌等信息；
- BM25 索引：支持词项匹配；
- 向量文件：支持语义近邻搜索。

如果这一步失败，先读日志最后几行。不要手动创建或修改 `release.json`，因为它是产物身份和兼容性检查的一部分。

### 第 2 步：训练排序器

点击 **2 训练排序器**。它读取 ESCI 的 train/validation 人工候选，计算两路召回分数和文本匹配特征，再按查询分组训练 LightGBM LambdaRank。

这里训练的是排序器，不是微调 MiniLM。训练完成后应能看到新的模型发布目录，其中包含排序模型、模型清单和新的发布清单。

你要能回答：为什么训练必须按 query 分组？因为排序目标是同一个查询内比较商品，不能把不同查询的商品混成一个排序组。

### 第 3 步：验证效果

点击 **3 验证效果**。它会在同一批 validation 查询上比较 BM25、dense、RRF 和 LTR，并生成逐查询结果、召回结果、耗时和错误分析。

完成后点击 **查看本轮结果**，回到结果解读页。比较新报告与已有报告时，先确认数据集、分区和截断值一致，再讨论指标差异。

一轮实验完成的标准是：

1. 每一步都有明确输入和输出；
2. 新目录没有覆盖旧目录；
3. 报告能够说明提升来自召回还是排序；
4. 你不会因为 validation 的一次变化就宣称线上效果提升。

### 中途停止和失败处理

点击 **停止当前实验** 会停止面板自己创建的进程，并保留日志和已经写入的文件。未完成目录不能当作成功发布包；排查后用“开始新一轮”生成新目录继续。

如果“建立索引”按钮因为目录已经存在而不可用，这是保护历史结果的正常行为。不要删除旧实验来解决，重新开始一轮即可。

## 场景四：从界面回到源码

进入 **学习路线**，然后按下面的顺序阅读。每读完一组，回到界面验证它对应的行为：

1. `schemas.py`：定义 Query、Product、Judgment 等数据边界；
2. `data/`：读取、清洗、分区，并把原始行转换成稳定结构；
3. `retrieval/`：分别实现 BM25 和向量检索，再实现 RRF；
4. `ranking/`：构造排序特征、训练 LambdaRank、加载模型并重排；
5. `service/search.py`：把查询编码、召回、融合、取商品和重排串成一次搜索；
6. `evaluation/` 与 `service/api.py`：分别负责证据和对外接口；
7. `cli.py`、`workbench.py`、`desktop.py`：把可复现流程和学习操作接到入口。

详细的文件构建顺序见 [`docs/FILE-GUIDE.md`](FILE-GUIDE.md)。面板的点击操作只是入口，算法仍然在这些业务模块中；这样你可以先理解流程，再逐个读代码。

## 常见情况

| 看到的情况 | 处理方式 |
|---|---|
| 双击后没有面板 | 确认项目根目录存在 `.venv/Scripts/pythonw.exe`；再看 `logs` 或用 `docs/COMMANDS.md` 的恢复步骤 |
| 点击搜索后提示模型缓存缺失 | 按 `docs/COMMANDS.md` 的环境恢复说明初始化 MiniLM 缓存；服务器没有 GPU 也可以使用 |
| 提示 8000 端口被占用 | 回到原来启动服务的终端正常停止；不要结束不认识的进程 |
| 结果报告没有出现 | 先确认 validation 任务以退出码 0 结束，再刷新已有资源 |
| 按钮不能重复执行 | 检查本轮是否已有对应产物；面板故意拒绝覆盖历史结果 |
| 搜索结果不理想 | 先查商品库覆盖，再区分没有召回和排序错误；不要直接改模型 |
| 想运行完整命令或 test | 阅读 [`docs/COMMANDS.md`](COMMANDS.md)，先完成 validation 和模型选择 |

## 进阶边界

本项目当前验证的是公开 ESCI 的 dev/validation 小规模流程。没有运行完整 US 目录的线上实验，也没有把 test 结果写成已经完成的事实。test 只有在模型选择结束后才应该冻结并消费；这一步保留在命令附录中，面板不会误触。
